# The Rang Intelligence — Architecture & Build Plan

Luxury Villa Revenue, Guest & Experience Intelligence Platform for The Rang Uluwatu.

This document is the reference architecture produced before implementation, per the brief's "FIRST TASK." It covers the pipeline, schema, folder structure, MVP scope, formulas, recommendation logic, AI architecture, UI wireframe and roadmap. The actual MVP code lives alongside this doc in the same project and is delivered as a downloadable, runnable codebase (see README.md).

## 1. Architecture — the pipeline

```mermaid
flowchart TB
    A[Data Ingestion\nCSV/XLSX upload: Booking.com, Airbnb, Direct, Reviews, Competitors] --> B[Data Cleaning\nvalidation, dedup, currency, mapping]
    B --> C[(PostgreSQL / SQLite)]
    C --> D[Analytics Engine\ndeterministic: occupancy, ADR, RevPAR,\nbooking pace, LOS, lead time, channel mix]
    D --> E[Forecasting Engine\n(Phase 2: trend + seasonal baseline)]
    D --> F[Recommendation Engine\nrule-based, thresholds vs history/competitors]
    E --> F
    F --> G[AI Interpretation Layer\nturns structured facts into plain-English narrative\nLLM if key present, deterministic templater otherwise]
    G --> H[Dashboard\nNext.js — Today / Revenue / Bookings / Guests /\nGuest Experience / Recommendations / Reports]
```

Every stage is a separate module. The AI layer never computes numbers — it only narrates numbers the analytics engine already computed, and is required to cite the underlying figures. When a metric can't be computed from available data, the system returns an explicit "Insufficient data" state rather than a guess.

## 2. Technology decisions (and why)

- **Backend:** Python/FastAPI, chosen over Next.js API routes because the brief explicitly separates ingestion → cleaning → analytics → forecasting → recommendation → AI into distinct modules; Python's data-handling ecosystem (pandas-free, hand-rolled for transparency) suits that better than colocating it in the frontend framework.
- **Database:** SQLAlchemy models targeting PostgreSQL in production (`DATABASE_URL` env var), with SQLite as the zero-config default for local/demo use so the MVP runs without installing Postgres first. Schema is identical either way.
- **Frontend:** Next.js 14 (App Router) + TypeScript + Tailwind CSS, Recharts for charts.
- **Auth:** email/password with JWT, single organisation/property for MVP (multi-property is a schema-level no-op to extend later — `property_id` is already a foreign key on every table).
- **AI:** pluggable `ai_narrative` service. If `ANTHROPIC_API_KEY` is set, narratives are generated by calling the Claude API with the computed facts as the only permitted source of truth (the prompt forbids inventing numbers). If no key is set, a deterministic template composer produces the same structured narrative style from the same facts, so the product is fully usable with zero AI spend and never blocks on an API key.
- **Deployment for this delivery:** this session runs in an ephemeral cloud sandbox with no persistent public URL, so the product is delivered as a complete, runnable codebase (docker-compose for Postgres + backend + frontend, or SQLite quick-start) rather than a hosted link. It was built and smoke-tested inside the sandbox before packaging.

## 3. Database schema (MVP tables)

- **properties** — id, name, address, bedrooms, currency, target_occupancy, target_adr, timezone
- **users** — id, property_id, email, hashed_password, name, role
- **channels** — id, name (Booking.com / Airbnb / Direct / Other), default_commission_pct
- **guests** — id, property_id, name (optional/minimisable), country, is_repeat, notes
- **reservations** — id, property_id, channel_id, guest_id, external_ref, booking_date, arrival_date, departure_date, nights, adults, children, gross_revenue, commission, net_revenue, adr (derived), currency, status (confirmed/cancelled), cancellation_date, lead_time_days (derived), promotion_id, source_detail, imported_batch_id
- **calendar_days** — id, property_id, date, is_available, min_stay, note (derived/maintained from reservations + manual blocks)
- **promotions** — id, property_id, name, discount_pct, start_date, end_date
- **competitors** — id, property_id, name, bedrooms, location, has_pool, has_sauna, ocean_view, review_score, review_count, notes
- **competitor_rates** — id, competitor_id, date, nightly_rate, available, min_stay, source (manual/csv)
- **reviews** — id, property_id, source (Booking.com/Airbnb/Google/Direct), review_date, rating, guest_country, raw_text, sentiment_score
- **review_topics** — id, review_id, topic (cleanliness/staff/pool/breakfast/…), sentiment (positive/negative/neutral), snippet
- **import_batches** — id, property_id, source_type, filename, uploaded_at, row_count, status
- **import_mappings** — id, property_id, source_type, column_map (JSON: "your column" → system field), remembered for reuse
- **recommendations** — id, property_id, category, severity (red/amber/green), observation, evidence (JSON), interpretation, action, expected_impact, confidence (high/medium/low), status (open/actioned/dismissed), created_at, target_start_date, target_end_date
- **operational_issues** — id, property_id, reservation_id (nullable), category, description, reported_date, resolved (Phase 2 stub table, present in schema)
- **expenses / campaigns / guest_messages** — present as stub tables in the schema for forward-compatibility (Phase 2/3), not populated by the MVP UI.

Full SQLAlchemy models are in `backend/app/models/`.

## 5. MVP scope (what is actually built and working now)

Built: auth, property setup, CSV/XLSX import with remembered column mapping and validation, reservation database, calendar view, revenue dashboard (occupancy/ADR/RevPAR/booking pace/lead time/LOS/channel mix) with period comparisons, basic guest segmentation, review upload + sentiment/topic tagging + review mining, rule-based recommendation engine with AI narrative layer, "What should I do today" dashboard, exportable weekly report, realistic labelled demo dataset so the app is usable immediately.

Explicitly deferred to later phases (schema has room for them, UI has placeholders/roadmap notes, nothing is faked): live OTA/API integrations (Booking.com, Airbnb, Google Reviews, Instagram, GA4, WhatsApp), competitor data beyond manual/CSV entry, statistical price-elasticity modelling, ARIMA/ML forecasting with confidence intervals, the full scenario planner, marketing-content-to-revenue attribution, and multi-property support. Section 39's later stages (forecasting, scenario planner, marketing intelligence, operational correlation mining) are architected for (tables/service stubs exist) but not built out — doing all 38 sections properly is a multi-month engineering programme, not a single build; the MVP is the genuinely-working foundation the brief asked to prioritise (Section 31/37).

## 6. Analytics formulas (deterministic, computed in Python — never by the AI)

- **Occupancy %** = booked nights ÷ available nights, for a date range.
- **ADR (Average Daily Rate)** = gross room revenue ÷ booked nights.
- **RevPAR** = gross room revenue ÷ available nights (equivalently ADR × occupancy).
- **Net revenue** = gross_revenue − commission.
- **Booking pace** at N days before arrival = % of eventual bookings for a date that were already on the books N days out, compared against the historical average of the same metric for the same days-before-arrival and season.
- **Lead time** = booking_date → arrival_date, in days; reported as mean/median per channel and period.
- **Length of stay (LOS)** = departure_date − arrival_date, in nights; mean/median/distribution.
- **Cancellation rate** = cancelled reservations ÷ total reservations for a booking-date cohort.
- **Channel mix** = revenue and reservation share by channel.
- **Comparisons**: current period vs previous period (same length, immediately prior), vs same period last year, vs trailing historical average (configurable window), vs competitor benchmark (median of manually-entered competitor rates for overlapping dates, only shown when ≥3 competitors have data for that window — otherwise flagged "insufficient competitor data").

## 7. Recommendation engine logic

Every recommendation is generated from a rule that compares a computed metric against a threshold derived from the property's own history (and competitor data where available), never from a hard-coded absolute number. Each rule emits the fixed structure: OBSERVATION → EVIDENCE (the actual numbers) → INTERPRETATION → ACTION → EXPECTED IMPACT → CONFIDENCE (High/Medium/Low, driven by sample size and data completeness).

Initial rule set implemented in the MVP:
1. **Low booking probability on approaching dates**: occupancy for a near-term window is materially below the trailing historical average for the same lead time/season, and the property's ADR sits above the competitor median for overlapping dates → recommend a bounded rate reduction and review of minimum-stay restrictions. Confidence scales with how many competitor data points exist.
2. **Strong demand window**: competitor availability for a window is low/falling and the property's own booking pace exceeds its historical average → recommend an ADR increase and explicitly advise against discounting.
3. **Slowing booking pace**: current pace at a given lead time is below the historical pace for that same lead time, with no clear competitor-availability explanation → flagged as a conversion/listing issue rather than a demand issue, since price and demand data don't explain it.
4. **Elevated cancellation rate**: cancellation rate for a recent booking cohort is a statistically meaningful step above the trailing baseline → flagged for investigation (e.g., promotion terms, deposit policy).
5. **Review-topic gap**: a topic with strongly positive sentiment (e.g., sauna, sunset) appears in a much smaller share of reviews than its sentiment strength would predict → flagged as a marketing/listing opportunity to feature it more prominently.
6. **Review-topic risk**: a topic trending negative over the last N reviews vs the trailing baseline → flagged as an operational risk.

Where the underlying sample is too small (e.g., fewer than 5 reservations in a cohort, or fewer than 3 competitors with overlapping data), the engine outputs "Insufficient data to determine this" for that specific rule instead of guessing, per the brief's anti-hallucination requirement.

## 8. AI architecture (narration only, never arithmetic)

`ai_narrative.py` takes the structured output of the recommendation engine (already-computed numbers + rule metadata) and produces the plain-English version shown on the dashboard ("Booking pace: ⚠️ Slower than normal" with a "Why?" drill-down to the raw numbers). It is explicitly forbidden — by prompt design when an LLM key is configured, and by construction when it isn't — from inventing any figure not present in the structured input. Two implementations share one interface:
- **LLM-backed** (`ANTHROPIC_API_KEY` present): calls Claude with the facts as the only allowed source of truth and a system prompt that requires citing them.
- **Deterministic templater** (default, no key required): fills the same OBSERVATION/EVIDENCE/INTERPRETATION/ACTION structure from string templates keyed to the rule that fired. This is what ships and runs by default so the product works immediately with zero configuration.

## 9. UI wireframe (see Design System note + built pages for the real thing)

Top-level nav: **Today · Revenue · Bookings · Guests · Guest Experience · Recommendations · Reports · Settings.** "Today" is the home screen and answers "What should I do today?" first: a status strip (occupancy, next arrival/departure, current ADR, upcoming empty nights), then an AI Actions feed of 🔴/🟡/🟢 cards in the OBSERVATION→ACTION→IMPACT format from the brief. Visual language: cream/warm-white background, charcoal type, muted taupe panels, a single restrained bronze accent for emphasis and status dots, serif headings, generous whitespace, no bright SaaS colours or gradients.

## 10. Roadmap

- **Phase 1 (this build):** everything in Section 5's "Built" list above, runnable locally today with demo data.
- **Phase 2:** forecasting engine with confidence intervals, price-elasticity estimation once enough price-variation history exists, scenario planner ("what if I drop price 10%"), fuller operational-issue correlation mining, weekly report scheduling/email delivery.
- **Phase 3:** legitimate API integrations (Booking.com/Airbnb connectivity where available, Google Reviews, GA4, Instagram), marketing-content-to-revenue attribution, multi-property support, automated (human-approved) rate push.

No feature in Phase 2/3 is simulated in the UI as if it already works — where the brief asks for it, the relevant screen either doesn't exist yet or is clearly marked as a roadmap placeholder, so the owner is never shown a fabricated forecast or a competitor price nobody entered.
